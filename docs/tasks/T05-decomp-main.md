# T05 — Decompile MAIN

**Status:** done (2026-10-09) · **Depends on:** T01 T02 T04

## Goal
Import the decoded MAIN image into Ghidra with the correct language and base address, auto-analyze it, and export the decompiled C to `decomp/main/`.

## Deliverables
- `docs/memory-maps.md` (MAIN section): language ID, base address, RAM/peripheral ranges, and how they were derived.
- `tools/ghidra/` headless scripts (import + export), reusable for T06–T08.
- `decomp/main/`: decompiled C split into files of a manageable size (e.g. per function or per address range), plus `INDEX.md` listing the notable functions found (CAT parser, string tables).

## Notes / hints
- Derive the base address from the vector table (reset/SP values) and absolute string pointers.
- Use a Ghidra script (e.g. Python/Java DecompInterface) to export. Keep each output file small so later agents can grep and read in pieces.

## Plan
1. Tooling: Ghidra 12.1.4 has no Renesas RX module. Search for a community SLEIGH RX/RXv2 module; inspect it (data files only, no Java/jar/scripts), install it per-user (`~/Library/ghidra/ghidra_12.1.4_PUBLIC/Extensions/`) and verify on the reset handler. Fallback: GNU binutils `--target=rx-elf` from ftp.gnu.org (signature-checked) into `~/.local/rx-binutils`, full disassembly instead of C.
2. Static recon with Python (`python3 -I`): fixed vector table 0xFFFFFF80..0xFFFFFFFF, reset code (SP/ISP/INTB setup, .data/.bss init tables), relocatable vector table, CAT mnemonic string and reply templates, candidate pointer tables.
3. Import with BinaryLoader at 0xFFF80000; a pre-script (`tools/ghidra/SetupRX651.java`) adds RAM 0x00000000 (256 KiB), the peripheral regions (0x00080000, 0x000A0000, 0x000C0000), the option-setting memory, models the .data copy-down (ROM image copied into RAM block), and seeds functions from both vector tables. Analyse with `-analysisTimeoutPerFile 3600` in project `ghidra/FT710_MAIN`.
4. Export with the shared `ExportDecomp.java` to `decomp/main/` (50 functions/file).
5. Locate the CAT parser and the mnemonic → handler dispatch table, the SCI0/1/2/3/5/7 drivers and the EEPROM SPI (RSPI) driver; write `decomp/main/INDEX.md` (plus a CAT dispatch table listing generated by a helper script).
6. Docs: MAIN section of `docs/memory-maps.md`, RX tooling in `docs/tooling.md`, Findings / Follow-ups / Status here.

## Findings
- **Tooling**: route 1 (Ghidra) worked. I installed the community RX SLEIGH module `stefan00lpf/rx-proc-ghidra` @ `ea4cd204`, data files only, as a per-user extension (`~/Library/ghidra/ghidra_12.1.4_PUBLIC/Extensions/RX`). The Homebrew install is untouched. Language `rx62t:LE:32:default`. Details and verification are in `docs/tooling.md`. binutils was not needed.
- **Load**: BinaryLoader at 0xFFF80000. Reset 0xFFF8FBDB sets USP=0x1004, ISP=0x1404, **INTB=0xFFF8E6DC**, EXTB=0xFFFFFF80, FPSW=0x100 **[fact]**. The CC-RX `_INITSCT` (0xFFFEDEDA) uses DTBL 0xFFF8E6A0 (3 copy-downs) and BTBL 0xFFF8E6C4 (3 zero-fills). All three copy-downs are modelled as initialized RAM blocks. The full map is in `docs/memory-maps.md` (MAIN).
- **Analysis**: 2254 functions; the export has 2252 non-thunk functions with **0 decompile failures**. ~384 KB of instructions, ~20 KB of non-0xFF ROM left undefined (mostly const data). Auto-analysis takes ~20 s. Output: `decomp/main/` (46 C files, `functions.tsv`, `cat_dispatch.tsv`, `INDEX.md`).
- **Compiler/runtime**: Renesas CC-RX with low optimization, and Renesas Code Generator / FIT style drivers (`R_SCIn_*`). It is a super-loop (`main_loop` 0xFFF94B8B) with no RTOS **[fact]**.
- **CAT**: parser `cat_parse` 0xFFFA347C. Primary mnemonics: 104 at 0xFFF805EC. Dispatch `cat_dispatch` 0xFFFA3B6E is a **switch with an int16 offset table at 0xFFF8F014 (104 entries) relative to the BRA.L at 0xFFFA3B8A**. Each case tests the total command length (read vs set) and calls `cat_XX`. Extended table: 10 at 0xFFF806BC (`SP EO E8 E9 FD KT PE ZZ VE JP`), dispatched by `cat_dispatch_ext` 0xFFFA3A2A, plus `cat_ext_SP` and `cat_ext_E9`. **These 10 are the main candidates for undocumented commands.** `BY ED EK EU RC RD RS RT RU XT` sit in the table but hit the switch default (error). 55 reply templates are at 0xFFF8F480. The full list is in `decomp/main/cat_dispatch.tsv` and `INDEX.md`.
- **UARTs**: SCI0 (USB Standard CAT), SCI1 (DISPLAY), SCI2 (tuner, maybe a CAT port too), SCI3 (USB Enhanced CAT), SCI4 (role unknown), SCI5 (SDR FPGA; `sdr_send_cmd` 0xFFFB1B2B), SCI6 (**simple-I2C mode**), SCI7 (C4/DSP). Functions are listed in `INDEX.md`.
- **EEPROM**: no RSPI is used. The BR25G256 is **bit-banged on port E** (PE0 /CS, PE5 SCK, PE6 MOSI, PE7 MISO): `eeprom_read` 0xFFFB14A4 and `eeprom_write` 0xFFFB14ED (64-byte pages, RDSR/WREN/WRITE) **[fact]**.
- A large code-pointer table at 0xFFF89D94 (4651 entries, 863 distinct handlers) is unexplained, probably the menu/UI **[inference]**.
  - *Answered (T10b, #71):* five 863-entry key handler tables indexed by key code, then two smaller tables (key slots 0xD..0x14 at 0xFFF8E100, the 296 EX-menu AI detectors at 0xFFF8E1A0); see [ui-keys.md](../code/main/ui-keys.md). #70 made all their targets functions.

- The image has ~244 B of undefined const data at 0xFFFEE1BE..0xFFFEE2B7 (worth a look), then 0xFF up to the version string and vectors. There is no bootloader in this image; the Renesas boot mode does the updates (see docs/hardware.md).
  - *Answered (#78):* the 244 B are code, not data: `_heap_find` (0xFFFEE1BE) and `malloc` (0xFFFEE239), the end of the CC-RX C library (stdio `freopen`/`fclose`/`fflush`, `free`, `sbrk`). Only `_INIT_IOLIB` and `_CLOSEALL` reach that library; `malloc` is called only by the unreferenced FILE allocator, so no part of the heap code runs. T21d (B5) made 0xFFFEE1BE a function, and the names are in `tools/ghidra/names_main.tsv`.
